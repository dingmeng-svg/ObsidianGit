# 知识库元数据规范 (Metadata Specification) v1.3

> 本文档是知识库所有笔记类型的元数据最高标准。所有新建笔记必须遵循本文档规定。
> **版本说明**：本文档使用 `v主版本.次版本` 格式。主版本变更（如字段增删、类型重构）时，需手动批量更新相关笔记的 Front Matter；次版本变更（如标签字典新增条目、措辞调整）向后兼容，无需迁移已有笔记。变更历史简要记录于本文档末尾的「变更日志」章节，仅保留最近3个版本，更早的历史通过 Git 提交记录追溯。

---

## §0 架构核心原则

### 原则一：`type` 字段的克制

`type` 字段仅用于具备专属模板且需高频 Dataview 查询的动态笔记类型。当前全库仅三种：

| type 值 | 笔记类型 | 存放路径 |
| :--- | :--- | :--- |
| `recipe` | 食谱 | 按领域归类 |
| `training_plan` | 训练计划 | 按领域归类 |
| `moc` | MOC 结构索引 | `32_MOCs/` |

其余所有笔记（通用知识、归档、原子笔记、读书笔记）**不设 `type` 字段**，统一用 `tags` 软分类。

> *为什么这样设计：避免为低频查询或静态内容创建冗余的类型枚举。`type` 是机器检索的强信号，应保持稀缺性以确保查询效率。*

### 原则二：出处信息的单一来源

-   文件名仅表达“这是什么概念”，保持纯净（如 `单点故障.md`）。
-   所有的作者、来源信息优先交给 YAML 的 `author` 和 `source` 字段维护。
-   仅当同名概念在不同出处有不同定义、需要消歧义时，才在文件名中加后缀（如 `系统（系统之美）.md` vs `系统（复杂）.md`）。
-   不推荐文件名后缀与 YAML 字段的双轨维护。

> *为什么这样设计：避免双重维护导致的信息不一致。当来源变更时，只需修改 YAML 一处即可全局生效。*

### 原则三：元数据与正文的分层

-   **元数据（YAML）服务于机器检索**：数值化字段用于 Dataview 排序/筛选，枚举值用于精确查询。
-   **正文服务于人类阅读**：详细描述、步骤说明、位置表格等深度内容放正文。
-   两者可表达同一维度的信息（如 `project` 字段 vs 正文位置表），但职责不同，互不替代。

> *为什么这样设计：让机器读结构化数据，让人类读自然语言。混合会导致查询性能下降和阅读体验割裂。*

### 原则四：全局基础状态与扩展状态分层

-   **全局基础状态**（`draft` / `active` / `archived`）：全库通用生命周期，跨类型查询的统一维度。
-   **类型扩展状态**（如 `mature`）：特定笔记类型在基础状态上的语义细化。扩展状态仅影响该类型的查询，不破坏全局过滤。

> *为什么这样设计：既保证了“所有活跃内容”的跨类型统计能力，又允许原子笔记表达“已完成提炼、稳定可引用”的成熟度信号。*

## §1 通用知识笔记标准

> ⚠️ **范围声明**：本节适用于不属于食谱、训练计划、MOC 的所有常规笔记。食谱和训练计划有独立的 Front Matter 标准（详见 §5、§6），包含更多专用字段，请勿混用本模板。

```yaml
---
title: "{{title}}"
date: {{date}}
status: ""              # draft | active | archived
tags: []                # 至少 1 个领域标签，从 §7 选取
aliases: []
related: []
pending_tag: ""         # 选填：当现有标签无法覆盖时填写建议新标签
---
```

| 字段 | 必填 | 说明 |
| :--- | :---: | :--- |
| `title` | ✅ | 文档标题 |
| `date` | ✅ | 创建或最后修改日期 |
| `status` | ✅ | `draft` / `active` / `archived` |
| `tags` | ✅ | 从 §7 标签字典中选取，**至少 1 个领域标签** |
| `aliases` | 选填 | 搜索别名 |
| `related` | 选填 | 关联笔记双链 |
| `pending_tag` | 选填 | 待归类标记，用于标签扩展缓冲机制 |

## §2 原子笔记标准

> 存放于 `31_Atomic_Notes/` 下的 `Concepts/`、`Models/`、`Critiques/`、`Practices/` 子文件夹。

### 文件名规则

-   **默认**：仅用概念名，如 `单点故障.md`。
-   **消歧义**：同名概念在不同出处有不同定义时，加后缀，如 `系统（系统之美）.md` vs `系统（复杂）.md`。
-   **不强制**：不要求所有原子笔记在文件名中标注出处。

### 标准模板（有明确来源）

```yaml
---
title: "单点故障：创业团队的致命脆弱点"
author: "萨姆·奥特曼 (Sam Altman)"
source: "[[创业公司从0到1的5层认知]]"
date: 2026-06-27
status: active
project: "知→行→进化"
tags: [概念, 工作]
aliases:
  - "创始人闹掰"
  - "战壕里的友谊"
related:
  - "[[创业公司从0到1的5层认知]]"
  - "[[股权分给员工：买心而不是买时间（创业认知）]]"
---
```

### 标准模板（原创框架）

```yaml
---
title: "可编程工作记忆：Hermes × Obsidian 架构原理"
date: 2026-06-26
status: mature
project: "知→行→进化"
tags: [概念, 技术]
aliases:
  - "可编程记忆"
related:
  - "[[外脑思考（卡片笔记写作法）]]"
---
```

### 标准模板（标准学术模型）

```yaml
---
title: "梅拉宾法则 (Mehrabian's Rule)"
author: "Albert Mehrabian"
date: 2026-06-08
status: mature
tags: [模型, 心理学]
aliases:
  - "7-38-55法则"
  - "非语言沟通的影响力模型"
---
```

| 字段 | 必填 | 说明 |
| :--- | :---: | :--- |
| `title` | ✅ | 概念/模型名称 |
| `date` | ✅ | 创建日期 |
| `status` | ✅ | `draft`(草稿) / `active`(仍在生长) / `mature`(已完成提炼，稳定可引用) / `archived`(已归档) |
| `tags` | ✅ | `[类型, 领域]`，类型为 `概念`/`模型`/`批判`/`实践`，领域从 §7 选取 |
| `source` | 选填 | 来源文件双链（如有源文件） |
| `author` | 选填 | 原作者 |
| `project` | 选填 | 归属项目，统一用 `知→行→进化` 箭头符号 |
| `aliases` | 选填 | 搜索别名 |
| `related` | 选填 | 同级原子笔记/源文件双链 |
| `human_edited` | 选填 | `true` = 人类编辑，AI 禁止覆盖正文；存量笔记默认 `true` | v1.4 |
| `ai_generated` | 选填 | `true` = AI 编译产物，未经验证 | v1.4 |
| `last_ai_edit` | 选填 | 最近 AI 增量修改日期，格式 `YYYY-MM-DD` | v1.4 |
| `ai_edit_summary` | 选填 | AI 修改内容简述 | v1.4 |
| `audit` | 选填 | 反馈信号，格式 `"high: 描述"` 或 `"low: 描述"` | v1.4 |

### 原子笔记状态流转

```
draft → active → mature → archived
  │                 │
  └─────────────────┴──────→ archived (任意阶段均可废弃归档)
```

-   `draft`：灵感碎片，概念尚未成型。
-   `active`：概念清晰，但仍在吸收新素材、持续打磨中。
-   `mature`：提炼完成，内容稳定，可作为其他笔记的可靠引用源。
-   `archived`：概念过时、被证伪或不再维护。

> *为什么需要 mature：区分“还在生长”的活跃笔记与“已完成提炼”的成熟笔记，让跨类型查询 `WHERE status = "active"` 时不会混入大量已完成但仍在原子笔记库中的静态内容。*

## §3 MOC 笔记标准

> 存放于 `32_MOCs/`。MOC 是笔记的结构索引，不是知识领域。

```yaml
---
title: "影响力的六大原则"
author: "罗伯特·西奥迪尼"
source: "《影响力》"
date: 2026-06-23
status: active
tags: [心理学]
aliases:
  - "影响力六原则"
related:
  - "[[互惠原则（影响力）]]"
  - "[[影响力法则检查清单（影响力）]]"
---
```

| 字段 | 必填 | 说明 |
| :--- | :---: | :--- |
| `type` | ✅ | 固定为 `moc` |
| `title` | ✅ | MOC 主题名称 |
| `date` | ✅ | 创建日期 |
| `status` | ✅ | `draft` / `active` / `archived` |
| `tags` | ✅ | 纯领域标签（如 `[心理学]`），**不使用 `知识管理` 标签** |
| `author` | 选填 | 原作者 |
| `source` | 选填 | 来源书名/链接 |
| `aliases` | 选填 | 搜索别名 |
| `related` | 选填 | 索引的原子笔记双链 |

**查询方式**：`WHERE type = "moc"`，不依赖文件夹路径。

## §4 归档文件标准

> 按 PARA 体系归档至 `40_Archive/` 的文件。归档是冷库，保持极简，不设 `type` 字段。

### 简单归档（默认）

```yaml
---
title: "香港生活成本备忘"
date: 2026-06-27
status: archived
tags: [归档, 生活]
---
```

### 读书笔记/总结类归档

```yaml
---
title: "《情绪词典》第一章：人与动物是如何感受的"
author: 朱建军
date: 2026-06-26
status: archived
tags: [归档, 心理学]
aliases:
  - "情绪词典笔记"
  - "感受的七个层次"
related:
  - "[[感受与感觉的区别（情绪词典）]]"
---
```

| 字段 | 必填 | 说明 |
| :--- | :---: | :--- |
| `title` | ✅ | 文档标题 |
| `date` | ✅ | 创建或归档日期 |
| `status` | ✅ | 固定为 `archived` |
| `tags` | ✅ | `[归档, 领域]`，领域标签从 §7 选取 |
| `author` | 选填 | 原作者（读书笔记适用） |
| `aliases` | 选填 | 搜索别名 |
| `related` | 选填 | 关联笔记双链 |

**注意**：归档文件**不设 `type` 字段**，不设 `project` 字段。需要区分类型时，用 `tags` 中的二级标签（如 `[归档, 心理学, 总结]`）。

## §5 食谱笔记标准

### 设计逻辑

1.  **时间数值化**：`prep_min` / `cook_min` 存纯数值，支持 Dataview 计算/排序，废弃 `total_time`。
2.  **分类数组化**：`cuisine` 支持层级标签，`course` 支持复合类型，支持 `contains()` 精确查询。
3.  **难度双轨制**：`level` (数值) 用于查询，`difficulty` (星星) 用于视觉感知。
4.  **多维筛选**：`main_ingredients` + `diet` 支撑“手头有X、偏好Y”的复合检索。

### 标准模板

```yaml
---
# === 核心信息 (必填) ===
title: "{{title}}"
cuisine: []              # [中式, 川菜] | [日式] | [法式, 普罗旺斯]
course: []               # [主菜, 配菜, 甜品, 酱料, 汤品, 沙拉, 开胃菜, 主食]
prep_min: 0              # 准备时间(分钟)，纯数值
cook_min: 0              # 烹饪时间(分钟)，纯数值
yield: ""                # "4人份" / "约500g" / "6寸1个"
level: 0                 # 1-5 (数值，与训练计划共享难度字典)
# === 食材与偏好 (选填但强烈推荐) ===
main_ingredients: []     # [牛肉, 番茄, 鸡胸肉]
diet: []                 # [生酮, 低碳, 纯素, 素食, 无麸质, 无乳制品, 低FODMAP]
# === 烹饪与记录 (选填) ===
difficulty: ""           # ★~★★★★★ (与 level 对应)
temperature: ""          # "100°C" / "180°C" / "中火"
rating: 0                # 1-5，5=反复做的核心资产
source: ""               # URL / 书名 / "自研改良"
# === 系统字段 ===
date: {{date}}
status: active
tags:
  - 生活/烹饪
aliases: []
related: []
pending_tag: ""
---
```

### `cuisine` 枚举参考

```yaml
# 顶层: 中式 | 日式 | 韩式 | 意式 | 法式 | 东南亚 | 中东风 | 美式
# 中式二级: 川菜 | 鲁菜 | 粤菜 | 苏菜 | 闽菜 | 浙菜 | 湘菜 | 徽菜 | 京菜 | 东北菜 | 西北菜

# 法式二级: 普罗旺斯 | 勃艮第 | 诺曼底 | 阿尔萨斯
```

## §6 训练计划笔记标准

### 设计逻辑

1.  **正交分解**：`goal_category` (宏观目标) + `focus_area` (解剖部位) + `skill_focus` (技能动作) 三维正交。
2.  **场景门槛前置**：`equipment` 与 `location` 数组化，执行前快速过滤。
3.  **生命周期管理**：`status` + `phase` + `last_review` 将静态笔记转为动态追踪。
4.  **数值与视觉分层**：`level` / `duration_min` 喂机器，`difficulty` 喂眼睛。

### 标准模板

```yaml
---
# === 核心信息 (必填) ===
title: "{{title}}"
goal_category: ""          # 体态纠正 | 力量提升 | 柔韧恢复 | 心肺耐力 | 专项技能 | 康复
level: 0                   # 1-5 (数值，用于查询)
duration_min: 0            # 单次预估分钟数 (用于查询)
# === 定位与场景 (必填) ===
focus_area: []             # [肩胛, 胸椎, 髋关节, 核心, 下肢]
equipment: []              # [徒手, 弹力带, 哑铃, 泡沫轴, 泳池]
location: ""               # 居家 | 健身房 | 户外 | 泳池
# === 状态追踪 (必填) ===
status: active
phase: ""                  # 进行中 | 迭代中 | 暂停 (业务子状态，仅 active 时使用)
last_review: YYYY-MM-DD
# === 辅助与系统 (选填) ===
skill_focus: ""            # "自由泳换气" / "引体向上离心控制"
difficulty: ""             # ★~★★★★★
cycle_weeks: 0             # 周期周数，0=日常持续计划
freq_weekly: 0             # 粗略每周次数，方便看板排序
source: ""                 # 自研 / 书籍 / 教练名 / URL
date: {{date}}
tags:
  - 生活/运动
aliases: []
related: []
pending_tag: ""
---
```

  - "自由泳训练"

## §7 YAML 书写规范（全库通用）

1.  `---` 独立成行，不黏内容。
2.  `tags` 不使用 `#` 前缀。
3.  双链引用用引号包列表格式：`related: ["[[笔记名]]"]` 或多行列表。
4.  修改后执行 `yaml.safe_load()` 校验语法。
5.  校对一次性做完，不回头补。
6.  正文不可残留 `## 关联笔记` 或 `## 它和什么相关` 区块——链接统一放在 YAML `related:` 字段。
7.  `project` 字段统一用 `知→行→进化` 箭头符号，不可写 `知行进化`。

## §8 标签字典

> 全库标签分两层：**领域标签**（描述知识领域）和**功能标签**（描述笔记角色）。每篇笔记至少 1 个领域标签。

| 标签 | 覆盖范围 |
| :--- | :--- |
| `生活` | 日常、家居、旅行、生活成本 |
| `生活/烹饪` | 食谱、烹饪技巧、食材知识 |
| `生活/运动` | 训练计划、运动生理、体态 |
| `心理学` | 情绪、认知、行为、人格 |
| `工作` | 职场、管理、创业、协作 |
| `技术` | 编程、架构、AI、工具 |
| `知识管理` | 笔记法、PKM、写作方法 |
| `金融` | 投资、理财、经济、商业 |
| `关系` | 人际、亲密关系、沟通 |
| `健康` | 营养、睡眠、医疗、康复 |
| `哲学` | 思维模型、伦理、存在主义 |
| `艺术` | 音乐、电影、设计、文学 |
| `语言` | 语言学、外语学习、写作 |
| `教育` | 学习方法、教学、成长 |
| `历史` | 历史、传记、文明 |
| `科学` | 物理、生物、化学、数学 |
| `素材` | 引用、金句、案例收集 |
| `系统文档` | 系统文档、系统文档、标准、本规范 |

### 功能标签（3 种）

| 标签 | 用途 |
| :--- | :--- |
| `归档` | 归档文件专属，与 `status: archived` 配合 |
| `概念` | 原子笔记——概念类 |
| `模型` | 原子笔记——模型类 |

> **补充说明**：原子笔记的 `批判` 和 `实践` 类型目前用 `概念` 或 `模型` 标签覆盖。如果未来这两类笔记数量增长，可追加 `批判` / `实践` 为独立功能标签。

### 标签扩展缓冲机制

当现有 18 个领域标签无法覆盖新领域时：

1.  先使用最接近的现有标签归档。
2.  在 YAML 中填写 `pending_tag: "建议新增标签名"`。
3.  每季度审查一次 `WHERE pending_tag != ""` 的笔记列表。
4.  当同一 `pending_tag` 值积累到 **5 条以上**时，正式将其纳入领域标签字典，并批量回改相关笔记。

### 标签使用规则

-   领域标签可多选（如一篇关于运动心理学的笔记可标 `[心理学, 生活/运动]`）。
-   功能标签通常单选。
-   `归档` 标签仅在归档文件中使用，与至少 1 个领域标签搭配。
-   `系统文档` 标签用于本规范、系统文档、模板等知识库自身维护文件。
-   子领域标签（如 `生活/烹饪`）自带父领域归属，无需同时标注 `生活`。

## §10 未来演进方向

> *`related` 字段语义化*：当前 `related` 保持简单无序列表格式，以平衡填写成本与当前 Dataview 查询能力。当 Obsidian 或 Dataview 原生支持结构化关系查询（如图遍历、关系类型过滤）时，可考虑升级为 `related: [{link: "", rel: "supports"}]` 格式。在此之前，鼓励用户在正文锚文本中明确描述关系性质。
