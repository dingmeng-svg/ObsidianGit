## 二、按频率分级的数据流
### 2.1 日级流（每天发生）
```

晨间 5min 全天 晚间 15min  
───────── ────── ──────────

60_Habits 灵感闪现 每日完成 ✓  
│ │ │  
▼ ▼ ▼  
50_BJ/Daily ← 00_Inbox → 10_Projects  
│ │ (更新进度)  
│ │ │  
├─ 习惯打卡 │ ▼  
├─ MIT 设定 │ 20_Areas  
└─ Rapid Logging │ (维护更新)  
│ │  
▼ ▼  
30_Resources 40_Archive  
(文献笔记) (完成项归档)

```

**日流特征：** 高频、碎片化、快速决策。重点不是完美分类，而是**不堆积**。

---
### 2.2 周级流（每周日）
```

周日 30min  
─────────

回顾 7 天 Daily Log  
│  
├── 未完成任务 → 迁移/分解/放弃  
│  
├── 00_Inbox 清零 → PARA 分类  
│  
├── 30_Resources → 提炼 1 条 → 31_Atomic_Notes  
│ │  
│ 当主题 ≥ 5 条时  
│ │  
│ ▼  
│ 32_MOCs  
│  
├── 10_Projects 审查  
│  
├── 60_Habits 周趋势汇总  
│  
└── 50_BJ/Future → 下周焦点设定

```
**周流特征：** 中频、深度加工。本周最重要的事：**提炼一条永久笔记**。

---
### 2.3 月级流（每月末）
```
月末 60min  
─────────

回顾 4 周 Weekly Log + Monthly Log  
│  
├── 完成的 Projects → 40_Archive  
│  
├── 过时的 Resources → 40_Archive  
│  
├── 61_Reviews/月复盘  
│ ├── 本月最大的收获  
│ ├── 本月最大的阻碍  
│ ├── 习惯趋势分析  
│ └── 下月焦点  
│  
└── 50_BJ/Future → 下月目标调整

```

**月流特征：** 低频、战略性。关注的是**模式**而非具体任务。

---
### 2.4 季级流（每季末）

```
季末 90min  
─────────

回顾 3 次月复盘  
│  
├── 61_Reviews/季复盘  
│ ├── 本季身份认同有变化吗？  
│ ├── 哪个领域进展最大？哪个停滞？  
│ ├── 知识体系有什么突破？  
│ └── 下季 3 个核心目标  
│  
├── 审查 32_MOCs 是否需要重构  
│  
└── 更新 60_Habits/身份认同.md

```

**季流特征：** 极低频、身份级。关注的是**我是谁**而非**我做了什么**。

## 三、PARA 四层间的数据流动

```
10_Projects ──────────────────────────────────────┐  
│ 有截止日、有交付物 │  
│ 项目完成时 ↓ │  
└──────────────────→ 40_Archive │  
↑ │  
20_Areas ─────────────────┤ │  
│ 持续维护、无截止日 │  
│ 领域不再活跃时 ↓ │  
└──────────────────→ 40_Archive │  
↑ │  
30_Resources ─────────────┤ │  
│ 参考资料、文献笔记 │  
│ 过时/已内化时 ↓ │  
└──────────────────→ 40_Archive │  
↑ │  
31_Atomic_Notes ────────────────┘  
32_MOCs （知识不会"过时"，  
但会被更好的理解替代）

```

**关键规则：**
- P → Archive：项目交付完成
- A → Archive：领域不再需要维护
- R → Archive：资料过时或已被提炼
- **永久笔记不进 Archive**，它们是你思想的底层基础设施

## 四、知识管理 知识加工流
```
数量多 ──────────────────────────────→ 数量少  
质量低 ──────────────────────────────→ 质量高

00_Inbox 30_Resources 31_Atomic_Notes 32_MOCs  
(50+ 条) (30+ 条) (10-20 条) (3-5 条)  
│ │ │ │  
│ 每天清零 │ 每周提炼 │ 当主题积累5+ │  
│ 1分钟/条 │ 15分钟/条 │ 30分钟/MOC │  
▼ ▼ ▼ ▼  
闪念笔记 文献笔记 永久笔记 索引笔记  
"灵光一闪" "别人说了什么" "我理解了什么" "它们如何关联"

生命周期： 生命周期： 生命周期： 生命周期：  
< 24小时 数周~数月 数年 持续更新
```
**提炼漏斗：**
- 每天 10 条闪念 → 3 条值得扩展 → 1 条变成文献笔记
- 每周 5 条文献笔记 → 1 条值得提炼 → 1 条永久笔记
- 每季度 10 条永久笔记 → 涌现 2 个 MOC

## 六、数据保鲜原则
| 层级 | 最大停留时间 | 超时后果 | 处理方式 |
|------|:--:|------|---------|
| `00_Inbox` | 24 小时 | 堆积→焦虑→废弃 | 日清零 |
| `Daily Log` 未完成任务 | 7 天 | 僵尸任务 | 周迁移 |
| `30_Resources` 未提炼 | 1 月 | 信息肥胖 | 周提炼 |
| `10_Projects` 无进展 | 2 周 | 伪项目 | 周审查 → 归档或复活 |
| `20_Areas` 未更新 | 1 月 | 领域腐烂 | 月审查 |
| `60_Habits` 未回顾 | 1 周 | 习惯退化 | 周日汇总 |

## 🆕 七、最小可运行单元：当时间表被打乱时
> 并非每一天都能完整执行时间表。出差、生病、突发紧急事务都会打乱计划。本节定义了系统的"最小可运行单元"——即使一天只有 15% 的执行力，这三个锚点也能让系统保持呼吸。
### 7.1 三个核心锚点

优先级从高到低：
```
┌─────────────────────────────────────────────┐  
│ 锚点 1：晨间 5 分钟（即使推迟到上午）            │  
│ □ 打开今天的 Daily Log                        │  
│ □ 习惯打卡（哪怕全是 — 或 ✗）                  │ 
│ □ 写下至少 1 条 MIT                           │  
│ 价值：用最小动作激活系统，宣告"今天我还在游戏里"   │  
└─────────────────────────────────────────────┘  
│  
▼  
┌─────────────────────────────────────────────┐  
│ 锚点 2：至少一段 50 分钟深度工作                │  
│ □ 可以在任何时段完成                           │  
│ □ 只要有一段不受打断的专注产出                  │  
│ 价值：确保今天有实质进展，而非只有"管理任务"      │  
└─────────────────────────────────────────────┘  
│  
▼  
┌─────────────────────────────────────────────┐  
│ 锚点 3：晚间 3 个复盘问题（5 分钟）             │  
│ □ 今天完成了什么？                            │  
│ □ 有什么卡住了？                              │  
│ □ 今天学到的一个东西？                         │  
│ 价值：不让今天的信息和洞察蒸发                  │  
└─────────────────────────────────────────────┘
```

### 7.2 可跳过的内容（按放弃成本从低到高排列）

| 可跳过的动作             |   放弃一天的代价    | 何时必须恢复                    |
| ------------------ | :----------: | ------------------------- |
| MOC 更新             |     几乎为零     | 当永久笔记积累到触发 MOC 创建的阈值时     |
| Areas 维护事务         | 低（可延后 2-3 天） | 当有维护事务即将在 7 天内引发危机        |
| Rapid Logging 完整记录 |  低（想法可能丢失）   | 当天有重要灵感或决策时不应跳过           |
| Inbox 清零           |  中（堆积增加焦虑）   | 次日必须清零；最多堆积 48 小时         |
| 习惯打卡全部写完           |      低       | 次日补记即可，但连续缺失超过 3 天会丢失趋势数据 |
| 阅读时段               |      低       | 连续缺失超过 3 天会影响心智习惯的连续性     |

### 7.3 中断恢复原则
> **不要补。继续。**
如果错过了某天的全部或大部分流程：
1. **不要试图补写前一天的 Daily Log**。那天的信息已经蒸发了，接受它。
2. **不要因为"昨天没做"而惩罚今天的自己**。系统不靠负罪感运转。
3. **直接打开今天的 Daily Log，从打卡开始**。
4. 如果在 Daily Log 中发现一个被跳过的日期，在对应文件里写一行：
   
   ```markdown
   ---
   ⚠️ 此日未记录。于 YYYY-MM-DD 确认跳过。
   
   ---   
   ```


然后关闭文件，不再回头看。

> 一个健康的系统不是永远不中断的系统，而是中断后恢复成本极低的系统。这三个锚点确保了：即使在最混乱的日子里，你也只需要 5 + 50 + 5 = 60 分钟就能让系统保持呼吸。
