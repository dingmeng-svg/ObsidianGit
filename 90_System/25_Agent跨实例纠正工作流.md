# Agent跨实例纠正工作流

> **本文为事后补救流程。事前预防机制见 [[双节点协作规范]]。**
>
> 当云端/本地双 Agent 协作时，一个 Agent 产生的错误记录如何被另一个 Agent 发现并纠正。

## 背景

丁萌的 Obsidian 知识库有两个 Hermes Agent 在维护：
- **云端**（腾讯云服务器）：跑 cron、A股复盘、数据采集
- **本地**（Windows PC）：日常知识管理、模板维护、Ingest

两者通过 Syncthing 双向同步文件，但**对话记录不互通**。

因此，一个 Agent 在日记/快照/Worklog 中写的推断性陈述，另一个 Agent 看不到原始对话上下文，无法验证真假。

## 问题示例

2026-06-29，本地 Agent 在 Daily 日记中写道：

```
* Note：主机发现 GLM-5.2 不如 DS 聪明，先不切换继续调教
```

这是一个**推断性陈述**——本地 Agent 在会话中观察到 GLM-5.2 响应慢，推断出"不如 DeepSeek 聪明"的结论并写入知识库。但实际上慢的原因是**14:30-18:00 高峰期限流**，而非模型能力问题。

## 纠正工作流

### 第一步：发现可疑推断

当你读到另一个 Agent 写的日记/Worklog/快照时，对以下内容保持警惕：

| 可疑信号 | 示例 |
|:---------|:------|
| 「主机发现…」 | 主语是 Agent 观察而非用户直接表态 |
| 「主机觉得…」 | Agent 在推测用户感受 |
| 「先不切换」、"继续调教" | 含有价值判断的行动建议 |
| 对比性结论（A不如B） | 需要验证的断言 |
| 「继续…」类行动指令 | 需要用户确认的下一步 |

### 第二步：向用户求证

不要直接修改或删除。先向用户提问，比如：

> 「我在 XX 文件中看到你写了『GLM-5.2 不如 DS』这条记录。这是你的原话，还是 Agent 的推测？」

### 第三步：按用户反馈修正

- **用户确认正确** → 无需操作
- **用户指出错误** → 按以下流程纠正：

1. **纠正源文件** — 用 `patch` 替换错误陈述为正确陈述
2. **写入记忆** — 将正确的事实写入 memory/user，避免自己再犯
3. **更新相关文件** — 如果 Worklog/快照也引用了该错误，一并修正

### 第四步：沉淀为工作流

如果这类问题反复出现，考虑：
- 更新 `obsidian-vault-manager` skill，加入审核规则
- 在 `90_System/` 中更新本 SOP

## 本案例完整操作记录

供参考——云端 Agent 在发现本地 Agent 写的错误记录后，实际执行的步骤：

```
1. 读到 Daily/2026-06-29.md 第46行错误推断
2. 向主人求证：「这是你说的还是本地Agent推测的？」
3. 主人纠正：GLM-5.2慢是因为14:30-18:00高峰期限流，不是模型笨
4. patch 纠正源文件中的错误陈述
5. 将正确事实写入 memory/user
6. 清理 user profile 中的重复条目释放空间
7. 输出本 SOP 沉淀工作流
```

## 原则

- **假设善意**：另一个 Agent 不是故意犯错，只是缺少上下文
- **推断非事实**：日记中的"主机发现/主机觉得"是推断，需要验证
- **先问后改**：未经用户确认不要直接删除/修改另一个 Agent 写的内容
- **沉淀固化**：每次纠正都应积累到 SOP 或 skill 中，避免重犯
