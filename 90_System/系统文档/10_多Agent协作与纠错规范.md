# 10_多Agent协作与纠错规范

> **地位声明**：本文由 24/25 合并而成，替代原两份文档。
> **版本**：v1.0.0 | **生效日期**：2026-07-13

> **定位**：云端/本地双 Hermes Agent 的协作协议与跨实例纠错规范。事前预防为主，事后纠正为辅。
> **前提**：两个 Agent 共享文件系统（Syncthing 同步），但对话记录不互通。

---

## 一、分工协议

| 任务类型 | 执行节点 | 规则 |
|:---|:---|:---|
| 所有定时任务（cron） | **云端独占** | 本地停掉所有与云端重叠的 cron |
| A 股复盘播报 | **云端独占** | 每日 18:18 触发 |
| 数据采集 | **云端独占** | 同上 |
| Ingest 编译 | **本地** | 用户显式触发，交互式任务 |
| 模板维护 | **本地** | 需要用户在 Obsidian 中即时验证 |
| 文件整理/归档 | **本地** | 需要用户确认决策 |
| Lint 健康检查 | **本地** | 避免两个 Agent 同时扫描全库 |

**不设主从关系。** 两个 Agent 各司其职，无主次之分。云端故障时本地不接管复盘任务，本地故障时云端不接管 Ingest。


## 二、故障感知

本地 Agent 启动时，或在每日 10:00 后首次收到用户消息时，执行只读检查：

1. 检查 T-1 日（昨日）的复盘文件是否存在于 `04_产出/股市数据播报/` 下
2. 不检查"当日"文件，因为当日复盘可能尚未到触发时间
3. 若 T-1 日和 T-2 日均无产出文件 → 触发告警：
   - 在 Worklog 中写入告警
   - 向用户发出提醒："云端复盘稿已连续 2 天未生成，请检查云端 Hermes 状态"

⚠️ 这是只读校验，不执行复盘任务。本地不接管云端职责。2 天窗口避免网络波动或休市误报。


## 三、写入纪律

1. **用户原话与 Agent 推断必须分离。**
   - 用户明确指令或陈述 → 可写入日记/笔记，标记 `source: user`
   - Agent 自身的观察/推断/建议 → **禁止写入用户日记正文或原子笔记正文**
2. **Agent 推断的唯一合法出口：Worklog（`90_System/Worklogs/`）**
   - 所有 Agent 推断、观察记录、待验证陈述统一写入当日 Worklog
   - 不使用日记中的 Callout 区块作为推断出口（对齐 HERMES v3.3 铁律 5）
3. **发现另一个 Agent 的可疑陈述时**，按第四章"跨实例纠正工作流"执行：
   - 先向用户求证，不直接修改或删除
   - 用户确认后修正源文件
   - 将正确事实写入 memory


## 四、跨实例纠正工作流

> 原 `25_Agent跨实例纠正工作流.md` 核心内容，本文为事后补救流程。

### 4.1 背景

丁萌的 Obsidian 知识库有两个 Hermes Agent 在维护：
- **云端**（腾讯云服务器）：跑 cron、A股复盘、数据采集
- **本地**（Windows PC）：日常知识管理、模板维护、Ingest

两者通过 Syncthing 双向同步文件，但**对话记录不互通**。因此，一个 Agent 在日记/快照/Worklog 中写的推断性陈述，另一个 Agent 看不到原始对话上下文，无法验证真假。

### 4.2 发现可疑推断

当你读到另一个 Agent 写的日记/Worklog/快照时，对以下内容保持警惕：

| 可疑信号 | 示例 |
|:---------|:------|
| 「主机发现…」 | 主语是 Agent 观察而非用户直接表态 |
| 「主机觉得…」 | Agent 在推测用户感受 |
| 「先不切换」、"继续调教" | 含有价值判断的行动建议 |
| 对比性结论（A不如B） | 需要验证的断言 |
| 「继续…」类行动指令 | 需要用户确认的下一步 |

### 4.3 向用户求证

不要直接修改或删除。先向用户提问，比如：

> 「我在 XX 文件中看到你写了『GLM-5.2 不如 DS』这条记录。这是你的原话，还是 Agent 的推测？」

### 4.4 按用户反馈修正

- **用户确认正确** → 无需操作
- **用户指出错误** → 按以下流程纠正：
  1. **纠正源文件** — 用 `patch` 替换错误陈述为正确陈述
  2. **写入记忆** — 将正确的事实写入 memory/user，避免自己再犯
  3. **更新相关文件** — 如果 Worklog/快照也引用了该错误，一并修正

### 4.5 沉淀为工作流

如果这类问题反复出现，考虑：
- 更新相关 skill，加入审核规则
- 在 `90_System/` 中更新本 SOP

### 4.6 原则

- **假设善意**：另一个 Agent 不是故意犯错，只是缺少上下文
- **推断非事实**：日记中的"主机发现/主机觉得"是推断，需要验证
- **先问后改**：未经用户确认不要直接删除/修改另一个 Agent 写的内容
- **沉淀固化**：每次纠正都应积累到 SOP 或 skill 中，避免重犯


## 五、信息共享格式

| 信息类型 | 存放位置 | 说明 |
|:---|:---|:---|
| 云端执行 cron 后的简报 | `90_System/Worklogs/YYYY-MM-DD.md` | 追加到当日 Worklog，使用固定格式（见下方） |
| 本地发现的可疑内容 | 同上，使用标题 `## ⚠️ 跨实例待确认` | 归集到当日 Worklog |
| 定期同步状态 | `90_System/记忆交接快照/` | 已有机制，继续使用 |

**不新建独立通讯目录。**

### 云端简报格式

云端 Agent 完成 cron 任务后，追加到当日 Worklog：

```markdown
## 云端执行简报
- 任务：[任务名称]
- 触发时间：[ISO 时间]
- 完成时间：[ISO 时间]
- 状态：ok / error
- 产出文件：[文件路径]
- from: cloud
```


## 六、启动协议

本地 Agent 启动时，必须执行以下步骤：

1. 读取最近 24 小时的 Worklog，建立云端执行状态感知
2. 若发现云端已执行某任务，本地跳过该任务的待办检查
3. 执行产出物完整性检查（见第二章）
4. 读取最近一份记忆交接快照
