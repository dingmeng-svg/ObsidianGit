## 一、核心铁律

### 1.1 文件操作安全

| 铁律 | 说明 |
|:---|:---|
| **write_file 前备份** | 文件已存在且内容将变更时，先 `cp` 备份 |
| **rename 后全库查引用** | 重命名后必须全库搜索旧名，批量更新引用 |
| **删文件前必请示** | 任何删除操作都先问再执行 |
| **归档时只移动指定文件** | 🔴 禁止清空目标目录（2026-07-11 数据丢失事故） |
| **创建后必验证可用性** | 检查 CSS 污染、双链引用、插件依赖 |

### 1.2 用户沟通风格

- **命令式、直接执行**：用户给任务后直接执行，不确认中间步骤
- **每阶段汇报结果**：执行完一批操作后清单式汇总
- **不要问"要xxx吗？"**：用户说什么就做什么
- **"播完通知我"模式**：批量任务做完通知即可，不更新进度
- **审计报告不夸大问题**：区分 P0（需立即修复）与 P1/P2（不紧急）

## 二、文件操作

### 2.1 原子笔记命名合规（NAMING-01）

**合规格式**：纯概念名，无后缀

| 状态 | 示例 |
|:---|:---|
| ✅ 合规 | `LLM Wiki.md`、`杀意未被转化的三种症状.md` |
| ❌ 冗余副标题 | `LLM Wiki：AI 驱动的知识库构建方法论.md` |
| ❌ 括号出处 | `蔡格尼克效应（心理学）.md` |

### 2.2 重命名执行流程

```
步骤1：全库搜索引用
  grep -r "旧文件名" --include="*.md" | grep -v "_备份"

步骤2：重命名文件
  mv "旧路径/旧文件名.md" "旧路径/新文件名.md"

步骤3：更新文件内容
  - YAML title 字段
  - 正文 # 标题

步骤4：批量更新引用（Python）
  for root, dirs, files in os.walk(BASE):
      dirs[:] = [d for d in dirs if "_备份" not in d]
      for f in files:
          if f.endswith(".md"):
              # 替换旧名 → 新名

步骤5：验证无残留
  grep -r "旧文件名" --include="*.md" | grep -v "_备份" || echo "✅ 无残留"
```

### 2.3 归档操作

**前置检查**：项目结项萃取。Agent 扫描项目目录并生成萃取建议清单，人类逐项决策后方可继续归档。

**系统文档废弃**：须执行前置依赖校验，详见 [[HERMES#系统文档废弃前置校验规则]]。

**核心铁律**：

| 铁律 | 说明 |
|:---|:---|
| **只移动指定文件** | 禁止清空目标目录 |
| **移动前检查目标** | 确认哪些需要保留 |
| **移动后验证完整性** | 原有 + 新增文件都存在 |

**归档流程**：

```
步骤1：检查目标目录内容
步骤2：列出需移动的文件（避免误删目标目录已有内容）
步骤3：执行移动
步骤4：验证文件数
```

**项目向导快照复用**：项目启动/结项向导同步复用 Ingest 流程的 Worklog 快照机制。中断时在当月 Worklog 中记录 `【流程快照】`，恢复时读取最新快照从断点继续。

## 三、双链维护

### 3.1 双链格式铁律

| 铁律 | 说明 |
|:---|:---|
| **必须使用双链格式** | `[[笔记名]]`，不是 `[笔记名]` 或 `[笔记名](路径)` |
| **禁止相对路径** | `[[../笔记名]]` 是错误的，使用 `[[笔记名]]` |
| **禁止 URL 链接** | `[文本](https://...)` 不是双链，不会被识别 |
| **目录链接必须加 `/`** | `[[目录名/]]` 打开目录，`[[目录名]]` 打开文件 |

**标准格式**：
```
[[笔记名]]
[[目录/文件名]]
[[笔记名|显示名]]
[[笔记名#章节]]
[[笔记名#章节|显示名]]
```

**目录链接**：

| 格式 | 效果 |
|:---|:---|
| `[[目录名/]]` | 打开目录的文件列表视图 |
| `[[目录名/文件名]]` | 打开目录下的具体文件 |
| ❌ `[[目录名/|别名]]` | **无效** — 目录链接不支持别名 |

**禁止格式**：

| 格式 | 问题 |
|:---|:---|
| `[笔记名]` | 不是双链，不会被识别 |
| `[笔记名](路径)` | Markdown 链接，不是 Wikilink |
| `[[../笔记名]]` | 相对路径不可靠 |
| `[[./笔记名]]` | 相对路径不可靠 |

### 3.2 重命名铁律

| 铁律 | 说明 |
|:---|:---|
| **重命名后必须更新全库引用** | 不允许残留旧引用 |
| **必须验证无残留** | 更新后全库搜索确认 |
| **MOC/Dataview 查询必须同步** | `FROM "旧路径"` 需要手动更新 |

**必检清单**：
- [ ] 全库搜索旧文件名（包括 `_备份` 目录）
- [ ] 更新 YAML `title` 字段
- [ ] 更新正文 `# 标题`
- [ ] 更新 `related` 字段中的双链
- [ ] 更新 MOC 和索引文件
- [ ] 检查 Dataview 查询是否用到旧路径
- [ ] 验证无残留引用

**特殊目录**：重命名后需额外检查：
- `C:\Users\丁萌\AppData\Local\hermes\skills\` — Skills 不在 Vault 内
- `90_System/SOP/` — 系统文档交叉引用密集
- `30_Resources/32_MOCs/` — MOC 是引用枢纽

### 3.3 断链处理铁律

| 铁律 | 说明 |
|:---|:---|
| **断链超过 3 条必须人工确认** | Agent 不自动删除或修改 |
| **断链 ≤ 3 条且路径确定可自动修复** | 直接 patch，事后汇报 |
| **删除笔记前必须检查入链** | 确认无引用后方可删除 |

**断链判定**：

| 类型 | 表现 | 处理方式 |
|:---|:---|:---|
| **真断链** | 目标文件不存在 | 需修复 |
| **假断链** | 文件存在但路径错误 | 自动修复 |
| **目录链接** | `[[目录]]` 而非 `[[目录/]]` | 视情况修复 |

**禁止行为**：
- ❌ 不检查入链直接删除文件
- ❌ 批量删除断链（可能是有意保留的占位符）
- ❌ 不验证就执行批量替换

### 3.4 建立对话链接规范

**强对话链接（必须注明理由）**：
```markdown
**强对话链接**：
- 链接至 [[笔记X]] | 理由：提供了机制解释
- 被 [[笔记Y]] 链接 | 理由：作为反例证伪了Y
```

**弱索引链接（允许留白）**：
```markdown
**弱索引链接**：
- 待链接：[概念/领域/案例] #待补理由
```

**禁止空洞词汇**：

| 禁止 | 正确 |
|:---|:---|
| ❌ "相关"、"类似"、"有意思" | ✅ 必须包含动词或关系名词 |
| ❌ `[[笔记X]]（相关）` | ✅ `[[笔记X]] | 理由：提供了机制解释` |

### 3.5 检查清单

**✅ 重命名后必检**：
1. ✅ 全库搜索旧文件名，确认无残留
2. ✅ 检查 MOC 和索引文件
3. ✅ 检查 Dataview 查询路径
4. ✅ 检查 Skills 目录引用
5. ✅ 验证新引用可点击跳转

**🔴 STOP 信号**（立即停止，人工确认）：
- ❌ 旧引用残留超过 10 处
- ❌ 不确定文件是否应该重命名
- ❌ 目标文件名已存在（会覆盖）
- ❌ 断链修复涉及删除操作

## 四、MOC 索引维护

### 4.1 MOC 创建门槛

**判定标准**：

| 类型 | 门槛 | 说明 |
|:---|:---|:---|
| **通用 MOC** | ≥ 5 条相关笔记 | 领域笔记数达到阈值才创建 |
| **特化 MOC** | ≥ 3 条相关笔记 | 子领域、特定主题 |
| **小众豁免** | ≥ 2 条相关笔记 | 专业领域判定见下节 |

### 4.2 小众专业领域判定标准

满足以下**任一条件**即为小众专业领域，适用豁免门槛：

| 条件 | 说明 |
|:---|:---|
| **学科壁垒** | 需专业背景才能理解（如量子计算、神经科学） |
| **工具特化** | 特定软件/框架专属（如 ComfyUI、TouchDesigner） |
| **产出稀缺** | 该领域原子笔记月增量 < 2 篇 |
| **范围封闭** | 与其他领域交叉少，自成体系 |

### 4.3 MOC 定位

| 维度 | 说明 |
|:---|:---|
| **本质** | 目录索引笔记，不是内容笔记 |
| **作用** | 导航枢纽，帮助发现和定位内容 |
| **位置** | 对应目录的根目录下 |

### 4.4 MOC 命名铁律

| 铁律 | 说明 |
|:---|:---|
| **必须与目录名一致** | `00_Inbox/00_Inbox.md`，不是 `00_Inbox/MOC.md` |
| **禁止使用 `MOC.md`** | 使用目录名作为文件名 |
| **禁止添加版本号** | `00_Inbox.md` 不是 `00_Inbox v1.0.md` |

### 4.5 MOC 放置铁律

| 铁律 | 说明 |
|:---|:---|
| **放在对应目录的根目录** | 不是 Vault 根目录 |
| **不要放在 Dataview 查询目标内** | 否则 Dataview 会抓取 MOC 自己 |
| **使用 WHERE 过滤排除自己** | `WHERE file.name != "MOC文件名"` |

### 4.6 MOC 文件位置

**标准位置**：

| 目录 | MOC 文件路径 |
|:---|:---|
| `00_Inbox/` | `00_Inbox/00_Inbox.md` |
| `10_Projects/` | `10_Projects/10_Projects.md` |
| `20_Areas/` | `20_Areas/20_Areas.md` |
| `30_Resources/` | `30_Resources/30_Resources.md` |
| `40_Archive/` | `40_Archive/40_Archive.md` |
| `90_System/` | `90_System/90_System.md` |

**子目录 MOC**：

| 目录 | MOC 文件路径 |
|:---|:---|
| `30_Resources/31_Atomic_Notes/` | `30_Resources/31_Atomic_Notes/31_Atomic_Notes.md` |
| `30_Resources/32_MOCs/` | `30_Resources/32_MOCs/32_MOCs.md` |

### 4.7 MOC 标准结构

| 序号 | 组成部分 | 说明 |
|:---:|:---|:---|
| 1 | YAML frontmatter | `title`、`date`、`tags: [MOC]`、`aliases` |
| 2 | 标题（带 emoji） | `📥 🚀 🌱 🧠 📦 ⚙️` 等 |
| 3 | 简短说明 | 1-2 句话描述该目录定位 |
| 4 | 📝 最近更新 | Dataview 动态列表 |
| 5 | 目录结构表格 | 子目录说明 |
| 6 | 各子目录 Dataview 列表 | 按领域分区 |
| 7 | 领域特定规则 | 如 ZK 核心规则、归档规则 |
| 8 | 相关文档链接 | 指向规范、操作手册等 |

**YAML 模板**：
```yaml
---
title: [目录名]
date: YYYY-MM-DD
tags: [MOC]
aliases:
  - "[旧名称]"
related:
  - "[[相关文档]]"
---
```

**Dataview 最近更新模板**：
```dataview
TABLE WITHOUT ID file.link AS "笔记", file.mtime AS "更新时间"
FROM "当前目录"
WHERE !startswith(file.name, "_") AND file.name != "MOC文件名"
SORT file.mtime DESC
LIMIT 15
```

### 4.8 MOC 更新时机

**必须更新 MOC 的操作**：

| 操作 | 说明 |
|:---|:---|
| **新增重要笔记** | 特别是原子笔记、项目笔记 |
| **重命名文件** | 更新 MOC 中的链接 |
| **移动文件到其他目录** | 检查 MOC 是否需要同步移动 |
| **创建新的子目录** | 在 MOC 中添加目录说明 |

**不需要更新 MOC 的操作**：

| 操作 | 说明 |
|:---|:---|
| **修改笔记内容** | MOC 只管索引，不管内容 |
| **修改笔记 YAML** | 不影响 MOC 结构 |
| **删除临时文件** | 临时文件不在 MOC 索引中 |

### 4.9 MOC 合并模式

当目录下存在旧 MOC 和新标准命名 MOC 时执行合并。

**合并流程**：
```
步骤1：先读旧 MOC内容
  └─ 保留有价值的结构化内容

步骤2：合并到新 MOC
  └─ 将旧内容融入新 MOC 对应位置

步骤3：删除旧文件
  └─ 合并完成后删除

步骤4：验证无残留
  └─ 检查旧文件确实已删除
```

**典型案例**：

| 旧 MOC | 新 MOC | 合并内容 |
|:---|:---|:---|
| `_Project_Index.md` | `10_Projects.md` | 进行中项目表、项目模板 |
| `Areas：My roles MOC.md` | `20_Areas.md` | 领域总览表、各领域详细说明 |
| `Archive 归档.md` | `40_Archive.md` | 归档分类表、各目录详细说明 |

### 4.10 MOC 自动聚合方案

新建 MOC 的核心概念列表使用 Dataview 自动聚合：

```dataview
TABLE WITHOUT ID file.link AS "笔记", file.mtime AS "最后更新"
FROM "30_Resources/31_Atomic_Notes"
WHERE contains(tags, "替换为对应标签") AND (status = "active" OR status = "mature")
SORT file.mtime DESC
```

**人工在 MOC 中只负责**：
- 「主题简述」：1-2 句话描述该领域核心特征
- 「概念间关系说明」：机器无法替代的高阶思考
- 「里程碑笔记置顶」：手动推荐 ≤ 5 篇核心笔记

人工手动置顶的核心笔记，必须在 MOC 的 YAML `related` 字段中添加双向链接。

**存量兼容**：存量混合式 MOC 不强制改造。新建 MOC 一律使用纯 Dataview 方案。月度审计不校验存量混合 MOC 的手动列表完整性。

### 4.11 Worklog MOC 特殊规范

**目录结构**：
```
90_System/Worklogs/
├── Worklog MOC.md
├── 2026-06/
│   ├── 2026-06-28.md
│   ├── 2026-06-29.md
│   └── 2026-06-30.md

    ├── 2026-07-01.md
```

**双链规范**：每个 Worklog 的 `related` 字段必须包含：

2. 前一天的 worklog
3. 后一天的 worklog

**示例**：
```yaml

  - "[[Worklog MOC]]"
  - "[[2026-07-08]]"
  - "[[2026-07-10]]"
```

### 4.12 检查清单

**✅ 更新 MOC 必检**：

- ❌ MOC 放在 Dataview 查询的目标目录内
- ❌ 不确定是否应该创建新的 MOC

## 五、Git 版本控制

Vault 已纳入 Git 版本控制。`.gitignore` 排除规则禁止手动修改，新增排除目录统一通过 Hermes 指令追加。

- 查看历史：`git log --oneline`
- 恢复单文件：`git checkout [commit] -- [文件路径]`

### 5.1 Git 初始化前置兼容要求

1. Vault 根目录路径禁止包含空格、中文、特殊符号
2. 已全局配置兼容中文文件名，无需重复执行
3. Windows 环境优先使用系统终端操作 Git 推送、克隆

### 5.2 Agent 自动提交与推送规则

**触发时机**：

| 触发事件 | commit message 格式 |
|:---|:---|
| 完成一项系统架构升级执行指令 | `[系统] 简短描述` |
| 批量 Lint 修复、断链清理、标签规整 | `[批量] 操作类型 N篇` |
| Skill/文档废弃退役、解绑 | `[生命周期] 对象名 操作` |
| Ingest 大规模编译（≥ 10 篇素材） | `[Ingest] 编译 N 篇素材` |
| 人类手动指令「快照备份」 | `[快照] 人类指定的描述` |

统一 commit 完整格式：`[模块-操作类型] 变更简述 | 影响文件数`

**提交前预检**（Agent 自动执行）：

1. **P0 断链标记**（不阻断提交）：检查是否存在新增 P0 文件级/Skill 依赖断链。若存在，不阻断提交，在 commit message 尾部追加 `[含P0断链]` 标记，提醒人类闭环。

2. **违规废弃阻断**（阻断提交）：检查是否存在已标记 `deprecated`/`retired` 但仍被 `related_system_docs` 或 `dependent_skills` 字段引用的文档/Skill。若存在，判定为「未解绑依赖违规废弃」，直接阻断自动提交，输出完整依赖清单，全部解绑后方可生成快照。

   **阻断后清理**：若判定为违规废弃并阻断提交，Agent **必须自动执行 `git reset HEAD .`** 撤销暂存区，确保不污染下一次合法提交。清理完成后再输出依赖清单和阻断提示。

   **说明**：废弃主校验在修改 YAML 状态字段时执行，本项仅为兜底安全网，拦截并发、遗漏导致的违规废弃。

**push 失败降级处理**：
- 若 `git push` 失败（网络异常、凭证失效等），Agent **不阻断**本地 commit 和后续工作流
- 必须在对话中明确提示：「✅ 本地提交成功，❌ 远程推送失败：[失败原因]。本地数据已受版本控制保护，但异地容灾未完成。请稍后检查网络或凭证后手动执行 `git push`。」
- 同时将此次异常写入当月 Worklog 的「异常说明」区块
- 若远程仓库持续推送失败（连续 4 次），次月 Lint 标记 P2 格式警告：「远程仓库推送持续失败，异地容灾已中断，请检查」

**提交防抖备注**（仅执行约束，不修改正文）：
- 若连续触发多次提交事件（如批量操作分多批执行），Agent 在最后一次操作完成后 60 秒内合并为单次 commit，避免 Git 仓库产生大量碎片化微小提交。

### 5.3 321 异地多介质备份策略

| 3份数据副本 | 实现方案 | 自动化规则 |
|:---|:---|:---|
| 本地工作库 | 电脑 SSD 日常 Vault 目录 | 每次修改自动纳入 Git 本地版本 |
| 外置冷存储 | 外置移动硬盘/NAS HDD 完整镜像 | 每周 Hermes 自动提醒同步，不阻塞主流程 |
| 异地云端副本 | Git 私有远程仓库 | 每次本地 commit 完成自动 push 推送 |

| 原则 | 实现 |
|:---|:---|
| 2 种存储介质 | SSD（日常读写）+ HDD/NAS（冷备份） |
| 1 份异地副本 | 私有 Git 远程仓库，满足异地容灾需求 |

**外置硬盘同步容错约束**：
1. Hermes 持久记录外置硬盘固定挂载路径；每周同步前自动检测路径是否存在
2. 硬盘未挂载、盘符失效：仅在当月 Worklog 写入提醒记录，不阻断 Git 提交、推送全流程
3. 连续 4 周检测不到外置硬盘挂载：月度 Lint 标记 P2 格式警告，提醒人工检查存储介质

**超大媒体文件约束**：
大于 10MB 图片、视频、压缩包已在 `.gitignore` 排除，仅本地 + 外置硬盘双留存，不上传远程仓库，防止仓库体积膨胀。

**仓库体积维护备注**（仅执行约束）：
- 当 `.git` 目录总大小超过 500MB，季度健康度快照追加提醒
- 人类可本地执行 `git gc --aggressive` 压缩仓库，不自动执行

### 5.4 灾难恢复标准化 SOP

**核心原则**：灾难发生时，**优先从 Git 远程仓库恢复，绝不动用 `_备份` 目录**（除非 Git 也损坏）。恢复完成后必须执行双重校验，方可正常使用 Vault。

#### 场景 1：Vault 整体损毁（硬盘故障、设备丢失）

1. 在新设备安装 Obsidian + Git
2. 克隆远程完整仓库：`git clone <仓库地址>`
3. 手动恢复本地 Obsidian 配置文件
4. 通过 Obsidian 社区市场重新安装插件
5. 从外置硬盘拷贝所有 `.gitignore` 排除的超大媒体素材
6. 执行全库断链扫描，确认数据完整性

#### 场景 2：单文件误删/误改

1. 发送指令：「恢复文件 [文件路径]」
2. Agent 执行：`git checkout HEAD -- [文件路径]`
3. 若需恢复到更早版本：「查看 [文件路径] 的历史版本」→ Agent 列出最近 5 次涉及该文件的 commit → 人类选择恢复目标
4. 恢复后校验：该文件 YAML 可解析 + 双链完整

#### 场景 3：批量操作需要整体回滚

1. 发送指令：「回滚到上一个快照」→ Agent 执行：`git reset --hard HEAD~1`
2. 若需回滚到指定快照：「回滚到快照 [commit前6位]」
3. 恢复后强制校验：全库 YAML 格式校验 + 全库系统文档断链扫描

**恢复后强制校验**（所有场景通用）：
1. `vault-management` 全库 YAML 格式校验
2. 系统文档交叉断链扫描
3. 若存在异常 → 输出清单，人工逐项修复
4. 校验通过后，方可正常使用 Vault

**人工操作高危约束**（执行备注）：
- 禁止人类终端手动执行 `git reset --hard`、`git push --force` 等高危命令
- 所有回滚、恢复统一通过 Hermes 自然语言指令操作
- 若手动误操作破坏仓库，优先重新克隆远程仓库修复

### 5.5 废弃/归档文件的版本留存

- 标记 `deprecated`、`retired`、`archived` 的文件**不物理删除**，仅修改 YAML 状态字段
- Git 历史永久保留其全部版本记录
- 废弃文件名前加 `⚠️` 前缀，如 `⚠️认知失调（旧版）.md`

**物理删除前置自动校验**：
- Agent 处理物理删除退役文件前，自动读取文件 YAML 中首次标记 `status: deprecated` 或 `status: retired` 的日期
- 计算标记日期距今的时间间隔
- 若不足 180 天 → **禁止删除**，输出：「[文件名] 标记退役仅 X 天，距 180 天观察期还有 Y 天，暂不可删除」
- 若超过 180 天 → 生成独立 commit：`[清理] 物理删除退役文件 [文件名] | 退役已满180天`，记录删除对象、标记日期、删除时间，然后执行删除

### 5.6 Remotely Save 多端同步

> **详细规范**：详见 [[09_图床与多端同步基础设施规范#四、多端同步层规范]]。
> 以下为操作要点，完整配置与故障排查以 21 号文档为准。

**技术链路**：
- 同步方式：S3 兼容存储（腾讯云 COS）
- 存储桶：`obsidian-sync-1309120115`（私有读写，与图床桶物理隔离）
- 子账号：`obsidian-sync`（仅同步桶读写权限）
- 忽略目录：`_备份_*/`、`.trash/`、`**/.git/`、`.obsidian/workspace.json`、`.obsidian/workspace-mobile.json`、`.obsidian/cache/`

**与 Git 灾备的分工**：

| 能力 | Git | Remotely Save |
|:---|:---|:---|
| 版本历史与回滚 | ✅ | ❌ |
| 异地容灾 | ✅（远程仓库） | ✅（COS 云端副本） |
| 多端实时同步 | ❌ | ✅ |
| 单文件误删恢复 | ✅ | ❌ |

两者互补，非替代关系。灾难恢复优先使用 Git，日常多端同步使用 Remotely Save。

**同步时机规范**：
1. 单设备编辑完成、关闭笔记面板后再触发同步
2. 多设备切换前，先在当前设备执行同步再退出
3. 大批量修改文档后，等待本地文件写入完成再同步

**离线编辑冲突处理**：
两台设备离线修改同一文件后，Remotely Save 会生成带时间戳的冲突副本。
1. 优先以 Git 最新提交版本为基准
2. 人工对比两份文件，合并内容后删除冲突副本
3. 重要系统文档修改后，同步完成务必手动提交 Git 固化版本

**其他设备接入**：在新设备安装 Obsidian 和 Remotely Save 插件，填入相同 COS 配置。首次同步前，临时将冲突解决方式设为「云端优先覆盖本地」，全量拉取成功后再恢复双向同步。

## 六、旧资产处置

> **定位**：当发现旧模板、旧方法论文档、历史项目残留等"旧资产"时，按此框架裁决去向。
> **核心原则**：减少重复决策成本。每次裁决后沉淀为判例，同类情况不再重新讨论。

### 6.1 裁决算法（4 步决策树）

对任意旧资产，按以下顺序执行决策树：

#### 步骤 1：是否仍在活跃使用？

- **判断依据**：该文件是否被以下任一活跃项引用？
  - `91_Templates/` 中的活跃模板
  - `10_Projects/` 中的活跃项目
  - `Bullet Journal/` 近 3 个月的日记
- **是** → **保留**，更新引用路径
- **否** → 进入步骤 2

#### 步骤 2：是否包含可独立复用的原子概念？

- **判断依据**：文件中是否有概念、模型、洞察可以脱离原文档上下文独立存在？
- **是** → **拆解零件**：提取原子概念写入 `31_Atomic_Notes/` 对应领域/类型，原始整体归档至 `40_Archive/系统文档/`
- **否** → 进入步骤 3

#### 步骤 3：是否属于已被否决的设计方向？

- **判断依据**：该文件是否属于以下任一情况？
  - 已被 v2.2 模板替代的旧模板（如 `季复盘模板.md`、`T_Video_Source.md`）
  - 已被负面清单否决的架构方案（如单文件 Inbox、合并 Habit Dashboard）
  - 指向已废弃的目录结构（如 `60_Habits/`、`50_Bullet_Journal/`）
- **是** → **归档**：移至 `40_Archive/系统文档/`，YAML 添加 `status: archived`，tags 添加 `[归档, 系统文档]`
- **否** → 进入步骤 4

#### 步骤 4：是否属于不确定的灰色地带？

- **判断依据**：无法明确归入以上三类
- **处理**：
  1. 保留在原地，不做移动
  2. 在 YAML 中添加 `audit: "low: 旧资产待裁决"`
  3. 下次 Quarterly Review 时集中处理

### 6.2 裁决触发条件

**何时应该启动此框架？**
- 在目录中发现文件名包含"旧版"、"v1"、"废弃"等标记的文件
- 在 `40_Archive/` 外发现指向已废弃目录的链接
- 在系统迭代中新方案替代旧方案时（如模板升级）

**何时不应启动？**
- 日常使用中的文件，即使修改时间较久（属于保鲜期管理，由 Hermes Lint 超时检测处理）
- 明确的活跃项目文件

| 资产 | 裁决 | 日期 | 理由 |
|:---|:---|:---|:---|
| `季复盘模板.md` | 归档 | 2026-06-29 | 被 Quarterly Template 替代 |
| `周复盘模板.md` | 归档 | 2026-06-29 | 功能融入 Weekly Template Callout |
| `月复盘模板.md` | 归档 | 2026-06-29 | 功能融入 Monthly Template Callout |

## 九、Lint 分级规则

### 9.1 问题分级

| 级别 | 名称 | 处理方式 |
|:---|:---|:---|
| **P0** | 阻断级 | 立即修复（如 YAML 解析失败、P0 断链） |
| **P1** | 重要 | 本次迭代修复（如 标签不合规、字段缺失） |

### 9.2 审计报告原则

- 区分 P0（需立即修复）与 P1/P2（不紧急）
- 不夸大问题，准确描述影响范围
- 提供可执行的修复建议

## 十、熔断规则

### 10.1 立即停止并人工确认

遇到以下情况**立即停止**，人工确认：

- ❌ 旧引用残留超过 10 处
- ❌ 不确定文件是否应该重命名
- ❌ 目标文件名已存在（会覆盖）
- ❌ 断链修复涉及删除操作
- ❌ MOC 文件名与目录名不一致
- ❌ MOC 放在 Dataview 查询的目标目录内
- ❌ 不确定是否应该创建新的 MOC

### 10.2 禁止行为清单

- ❌ 不检查入链直接删除文件
- ❌ 批量删除断链（可能是有意保留的占位符）
- ❌ 不验证就执行批量替换
- ❌ 清空目标目录（归档时只移动指定文件）
- ❌ 物理删除未满 180 天观察期的退役文件
- ❌ 人类手动执行 `git reset --hard`、`git push --force` 等高危命令
